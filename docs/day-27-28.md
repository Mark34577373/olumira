# Days 27–28: personalized communication and shared care

Both milestones extend the existing Flask/Jinja application. No dependencies,
services, environment variables, commits, pushes or deployments were added.

## Day 27 — communication for each profile

Select a care profile, then open Communication → **Display & speech preferences**.
Settings persist on the server across refresh, login, caregivers and devices:
large/medium/compact cards; board/adaptive/2/3/4-column grids; label placement;
labels/pictures visibility; speech enabled/rate/preferred voice; stronger contrast;
reduced movement; simplified mode; and the default board. At least pictures or
labels must remain visible. Screen-reader names stay available when visible labels
are hidden. Phone grids stay within the screen and use at most two columns.

A live preview changes the draft; only Save persists. Versions reject conflicting
caregiver edits. Speech still offers only browser-designated local voices, handles
asynchronous loading/errors, cancels overlapping speech, and falls back to another
available local voice when a preferred device voice is unavailable. No identical
voice or audible/offline behavior across devices is promised. Profile preferences
are authoritative when reopening a board; player speech controls are visit-local
overrides. Workspace-level boards retain their existing browser preference behavior.

**Open my communication** opens the active profile's saved default board. Archived
or inaccessible defaults are skipped, falling back to favorites or the library.
The player shows an active-board switcher, favorite choices shortcut, clear exit
and a reversible **More/Fewer controls** switch. Simplified mode uses larger cards,
fewer navigation choices and hides secondary speech/save controls while retaining
written messages, speech/stop/replay, removal, back and exit. Toggling modes never
navigates or discards the current message.

**Manage favorites** adds/removes/reorders picture and phrase references for this
profile; no duplicated phrase text is stored. Composite primary keys prevent
repeated favorites, and retries express desired add/remove states rather than
blind toggles. Up to 50 favorites of each kind are supported. Archived source items
stay visible to the caregiver manager but are hidden in the communication view;
restoring a source makes it available again. Deleted cards cascade out of favorites.
Settings/default/favorite references are workspace/profile-validated in services and
DB guards. Boards used as defaults or favorites must be duplicated for reassignment
rather than silently invalidating a profile's configuration.

Favorite choices opens its own focused board. Its refresh identity includes source
board/phrase versions and archive/deletion state, so an already open view detects
stale source content. The main board also checks preference versions. Known access
loss clears/stops use; a change asks for reopening while preserving the current
written message. Profile selection from Communication opens the selected profile's
own default/favorites/library. Transient utterances remain page-memory only and
clear on navigation; another profile's words never become its draft.

Workspace-wide communication remains available without a profile. Personalization
requires an explicitly selected care profile; there is no implicit global default
published from old browser settings. Viewers use personalized boards and favorites
but cannot change shared preferences or favorite lists.

## Day 28 — responsibilities and handoffs connected to care

**Care team** in the horizontal navigation contains Responsibilities, Handoffs and
Shared activity, scoped to the active profile or workspace-wide context. There is
no permanent sidebar. All reads require current verified membership; all mutations
use central `care.manage`/`care.acknowledge` permissions, CSRF, workspace context
binding and workspace-first locks. Owners/caregivers manage; viewers read only.

Tasks support a bounded title/description, profile, active owner/caregiver assignee
or unassigned state, optional routine, priority and optional due time/IANA zone.
Only same-workspace members and same-profile linked routines are accepted. Removed
or viewer members cannot receive assignments. Historic assignments remain named
with a reassignment prompt; an inactive assignment must be explicitly changed
before saving an edit. Saved tasks keep their original profile; create a new task
for another profile to retain history association.

Statuses are To do, In progress, Completed and Canceled. Completed/canceled tasks
can be explicitly reopened; completion time/actor are recorded and earlier events
remain in activity. Desired-state completion retries do not create duplicate events.
Versioned metadata/status changes reject stale conflicting edits rather than silently
overwriting them. UUID creation intents prevent duplicate task creation on retry.
Views include My tasks, All authorized tasks, upcoming seven days, overdue, completed,
assignee/status filters and the existing profile selector, with 20-row pagination.
Dates are stored in UTC and shown in their stated IANA zone. Past dates are allowed
and appear overdue; spring gaps are rejected and autumn repeated times use the
first occurrence. At most 200 tasks may be open per profile/workspace context.

Handoffs save a practical summary, profile, another active caregiver or the current
team, up to ten task references, and optional routine/observation references.
Observation content is not copied into the handoff. A scoped private detail route
lets authorized readers inspect the original observation when needed. Choose the
active profile before linking its care; every posted reference is validated even
when its ID was not offered by the form.

Team recipients are snapshotted individually from other active owners/caregivers at
creation. Each intended recipient can acknowledge once; retries are harmless.
Creators and other members cannot acknowledge for a recipient, and viewers cannot
acknowledge. Summaries/recipients and saved acknowledgments are immutable. Removal
never fabricates acknowledgment: pending former recipients remain explicitly
marked as no longer active. Handoff history supports profile/date/status and pending
inbox filters, 20-row pagination, and per-person status/time. There is no editing or
hard deletion of shared handoff history. A profile's retained handoffs are capped at
1,000; production retention/export needs review before expanding beyond that bound.

The activity timeline reuses existing immutable audit events through an explicit
user-facing allowlist and scoped live target lookups. It includes guided routine
completion, task assignment/completion, handoff creation/acknowledgment, observations
added and communication boards updated. It excludes security events and never
previews observation notes or spoken/saved phrase contents. No duplicate event store
or historical activity is invented. Events for reassociable legacy targets follow
their current authorized association; historical actors' current display names are
used. Lists fetch bounded pages; dashboard widgets use three tasks, three pending
handoff links, a real pending count and three relevant events rather than loading
entire histories.

The existing email outbox is for identity flows, not a general notification system.
Task/handoff states are clearly visible in-app. Advanced/email notifications are
explicitly deferred to Day 38, as permitted by the brief.

## Schema and operations

- `0012`: `communication_preferences`, `favorite_communication_cards`,
  `favorite_communication_phrases`.
- `0013`: `caregiver_tasks`, `caregiver_handoffs`, `handoff_recipients`, `handoff_tasks`.
- Additive tables/indexes only. FK/uniqueness constraints and SQLite/PostgreSQL
  guards protect profile/default/favorite/reference/assignee scope and immutable
  handoff/acknowledgment/task associations. Existing rows/columns are preserved.
- The legacy-only transfer now requires head **0013** and refuses these tables
  rather than dropping personalized or caregiver data.
- No new paid APIs, dependencies, secrets, background workers or environment values.
  Existing signing/encryption keys, verified login, Redis and SMTP requirements stay.
  Custom media uploads remain disabled pending durable private media storage.

Quiesce writers, take and verify a complete private backup, then run
`venv/bin/python -m flask --app app db upgrade` and restart the existing
`gunicorn app:app` or local Flask server. Startup does not migrate automatically.
Review PostgreSQL SQL and verify live PostgreSQL/Redis behavior in staging when
those disposable services are configured; offline SQL/SQLite tests do not prove it.

Smoke test profile preferences/defaults/favorites across two browsers, profile
switching, local voice fallback, task assignment/stale edits/completion, individual
and team handoff acknowledgment, removed-member behavior, private references,
viewer/family denials, dashboard counts and mobile/keyboard layouts. Check head
0013, integrity/FKs, private cache headers and existing login/recovery flows.

Both downgrades refuse unreviewed deletion. Rollback requires stopped writers,
an incident snapshot, verified pre-upgrade backup, matching prior code/keys and
review/reconciliation of any subsequent real activity. Do not automatically deploy.

## Fictional demonstration and tests

Run `venv/bin/python scripts/preview_routines.py --port 5055`; credentials are written
to the private temporary file printed by the process. The isolated temporary database
contains Fictional Fern, profile preferences/default board/card favorites, saved
phrases, guided routines, tasks assigned to Fictional Sage and pending handoffs.
Normal verified-account services and membership rules are used; the real DB is not
opened by the script. Preview changes last until the process stops.

1. Select Fictional Fern; adjust display/speech settings and favorites.
2. Open personalized communication, build a message and use local speech if available.
3. Return to Care team; create a routine-linked task assigned to Fictional Sage.
4. Sign in as Sage, open My tasks, complete it, and inspect shared activity.
5. Create a handoff with related task/routine/observation and choose Sage.
6. Sage acknowledges; both caregivers can inspect status/history and safe activity.
7. Confirm viewer use without edits and unrelated-family 404s.

Commands:

```sh
venv/bin/python -m pytest -q
venv/bin/python tests/browser/check_personalized_care.py
venv/bin/python tests/browser/check_communication_boards.py
venv/bin/python tests/browser/check_ui.py
venv/bin/python -m pip check
venv/bin/gunicorn --check-config app:app
```

Browser tests use fictional records and local-voice mocks; real audible output and
formal accessibility certification are not claimed. See [executed evidence and
milestone reports](day-27-28-verification.md).
