## Day 33 — Unified calendar and reminders

Completed: month/week/day/14-day agenda, date/previous/next/today navigation, type filtering, active profile context, saved view selection, real routine schedules/completed occurrences, dated tasks and handoffs. Custom event series support create/detail/edit/reschedule/cancel/archive/restore, optional caregiver assignment, all-day events, timezone and daily/weekly/selected-weekday recurrence. The service reuses existing routine recurrence/DST calculations instead of a second engine. Long events appear on every overlapping day. Compact mobile month dates expose counts and open the full day view.

Personal reminder preferences persist per user/workspace/profile: enabled, 0/15/60/1440-minute lead time and routine/task/event types. In-app reminders are computed from stored events on calendar/dashboard load. Overdue tasks cover seven days; routine/event attention covers the recent day or an ongoing event. Canceled/completed/archived records are excluded. These are not browser timers. Background email/push delivery is deferred to Day 38.

Files: `services/calendar.py`, `olumira/routes/calendar.py`, `templates/calendar/*`, calendar models, central permissions/registration/navigation/styles; migration **0015** adds event and reminder tables with scope guards. The existing recurrence display window now supports up to 42 days for month views. No recurring routine or task records are duplicated by calendar reads.

Security/accessibility: fresh role checks, exact workspace/profile queries, CSRF, version conflicts, scoped assignees, creation-key replay protection, confirmation before series status changes, native labeled controls, keyboard links and mobile date targets. All-day ends are exclusive. Nonexistent DST occurrences are skipped; repeated clock times use the first occurrence. Local wall-clock end times recur with the start; an occurrence with a nonexistent end clock is skipped. Edits/status changes apply to the whole custom series; there are no per-occurrence exceptions or drag rescheduling. Limits: 500 custom series per profile, 3,000 displayed occurrences and at most 42 displayed days; no silent truncation of the main calendar.

Tests: `tests/test_calendar.py`, four focused tests passed, including real scheduled routine/task integration, all views, recurrence/DST, CRUD/status/version/replay, reminders, roles, CSRF and profile/workspace isolation. The browser scenario exercises the real forms and all views. Final results: [verification](day-33-36-verification.md).

Manual: Calendar → New event → enter local times/timezone/recurrence → Save → select a date. Edit/reschedule, cancel with confirmation, archive, then restore. Reminder preferences → choose categories and lead time → Save. Schedule an existing routine and assign a dated task to see them in the same calendar.

Additive chain: **0014 → 0015 → 0016 → 0017 → 0018**. Six new tables; existing tables/records remain intact. Resources are seeded once by migration. Downgrades deliberately refuse unreviewed loss of the new records. The legacy transfer utility recognizes head 0018, refuses nonempty new personal tables, and verifies unchanged curated resources rather than discarding edited curation.

```sh
venv/bin/python -m flask --app app backup-sqlite --source database/olumira.db --backup database/backups/before-day33-36.db
venv/bin/python -m flask --app app db upgrade
venv/bin/python -m flask --app app db current
venv/bin/python -m flask --app app run --port 5000
venv/bin/python scripts/preview_routines.py --port 5059
```

Use an unused backup filename; never overwrite a recovery snapshot. The disposable preview uses a temporary database and separate cookie/key. Its fictional accounts use the real development verification-token flow; credentials are written to a private temporary access file. `welcome-preview@example.com` starts the first-use journey; `preview@example.com` has populated family data. Preview changes last until its process stops. No real SMTP inbox-delivery result is claimed.

No new runtime dependencies or environment variables. Render remains Flask/Gunicorn, PostgreSQL, Redis, trusted HTTPS/proxy settings, stable keys and the existing configured mail worker. Run migrations before restarting workers. In-app reminders need no background process; email/push reminder delivery is deferred. PostgreSQL offline migration SQL and Gunicorn configuration are checked, but live PostgreSQL and hosted load/smoke tests remain release gates. Rollback requires a reviewed backup/code recovery plan, not a destructive reset.
