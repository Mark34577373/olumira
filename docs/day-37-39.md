# Olumira premium experience phase 2 — Days 37–39

## Implemented scope

Day 37 adds `/settings`, reachable from Account, with responsive section links to existing secure account/email/password/session management, dashboard/profile/timezone, calendar reminders, profile communication and owner workspace controls. The new `UserPreference` contains only personal display and calendar presentation settings: larger text, reduced motion, enhanced contrast, simplified decoration, reduced shadows, calendar view, week start and clock format. Light appearance and English are supported; no unsupported theme/language selector is shown. OS reduced motion and contrast preferences apply automatically. Existing dashboard timezone/profile/widgets, communication board/card/speech settings and reminder preferences remain their original sources of truth. Viewer members may save their own settings without acquiring permission to edit shared care records. Saves use an explicit allowlist, validation, optimistic versions, user serialization and normal CSRF enforcement. Presentation changes do not rewrite event timestamps.

Day 38 adds a notification bell with unread count/three generic previews, a paginated 20-item inbox, category/status filters, read/unread, dismiss, mark-all-read and POST-based authorized navigation. Notifications are created for real task assignment/reassignment, handoff requests and acknowledgment. Titles exclude care-profile names, task titles, observations and private notes. Scope provenance has database foreign keys to the recipient membership and matching profile/workspace. Membership, role and entity scope are rechecked on open; changing profile context remains an authorized explicit action. Recipient/workspace queries are indexed and bounded. No polling is required. Optional categories and retention are member-owned per workspace; existing account-security mail is unaffected.

`process-reminders` uses the existing calendar, recurrence revisions and DST resolution for routines, tasks and custom events. It reads existing per-user/profile lead times and categories, respects inbox categories and fresh active memberships, and persists each generic in-app reminder in its own member/profile transaction. Workspace locking plus unique SHA-256 deduplication keys make retries/concurrent workers safe. Occurrence identity and start instant distinguish recurring dates and rescheduled starts. Old unread actionable reminders are dismissed when canceled, completed, paused, superseded or disabled; history rows are not rewritten. Started/completed routine runs do not generate approaching reminders. The processor catches up over 24 hours; outages longer than that do not cause unlimited historical notifications. Assignments/handoffs are immediate business events, independent of this command. Invitations and identity/security events continue through the existing email outbox; they are not represented as invented inbox categories. Reminder email and mobile push are unavailable.

Day 39 adds `/settings/privacy` with real personal/workspace JSON exports, current-password verification, single-use five-minute grants, typed closure confirmations, owner addition for sole-owner resolution, session/security links and accurate retention information. Personal exports include the account and that user's own preferences/bookmarks/onboarding/inbox across workspaces, excluding shared care records and other caregivers. Owner workspace exports include all care profiles and reviewed shared care tables plus child records selected through authorized parents. Credentials, session handles, mail payloads, invitation secrets and other members' personal preferences/inboxes are excluded. JSON avoids spreadsheet formula execution; the existing separate CSV report protections remain unchanged.

Export requests contain metadata and hashed download tokens only. Tokens are submitted in CSRF-protected POST bodies, never query strings or public links. Download authorization and owner role are rechecked; a grant is consumed only after bounded generation succeeds. Generation is capped at 10,000 records and 8 MiB, with chunked database iteration and no server export files. Oversized exports give an operator-assistance message. Fixed filenames and `private, no-store` responses prevent unsafe names/caching. Requests and downloads in a workspace are audited. Account-only grants also work after the last workspace has closed.

## Deletion and retention policy actually implemented

Account deletion immediately anonymizes identifying fields on the account, randomizes its password, marks it permanently closed, clears pending email, advances credential generation, revokes every stored session and active membership, invalidates recovery tokens/cancels queued mail, and removes personal preferences/bookmarks/inbox/download grants. The immutable shared authorship UUID and authored care history remain; those records are not silently destroyed. Closed accounts cannot authenticate, start sessions, consume recovery tokens or accept invitations. A persistent deletion-review record records completion of access closure/anonymization.

An account cannot close while it is the sole active owner of any open workspace. An owner can add another verified current member as an owner with reauthentication and workspace locking. Owner authority is clearly explained; arbitrary other-workspace identifiers are rejected. The original owner remains an owner until account closure. Alternatively an owner can close a workspace. Closing all workspaces does not trap the account: Privacy remains available to finish account deletion or a personal export without an active workspace.

Workspace closure requires owner permission, current password, exact scope and `CLOSE WORKSPACE`. It marks the workspace closed, revokes all member access, cancels invitations/queued invitation mail, invalidates download grants and records an audit event/deletion-review record. Every membership lookup excludes closed workspaces. **It does not physically purge shared care records, immutable history or backups.** This is an actual access-closure and erasure-review workflow, not a claim of complete erasure. Operator-reviewed physical erasure is a separate process; no automatic cascade purge or public restore has been introduced. Failure rolls back the operation; there is no misleading success response after a failed transaction.

`privacy-maintenance` removes expired download grants and read/dismissed notifications after the member's selected 30/90/180 days (default 90), measured from read/dismissal time. Unread notices remain. It never purges observations, routine history, archived records, audit events, deletion-review records or invitations based on a generic age. Existing expired invitations cannot be accepted, but this milestone does not promise their automatic physical removal. No export temporary files exist to clean up. Local development email previews and manually made backups are operator-managed and are not covered by inbox retention.

## Backup audit and recovery safeguards

`backup-sqlite` uses SQLite's backup API, an exclusive unused destination and mode 0600. Local backups are full database copies under the ignored `database/backups` directory. A real pre-upgrade copy was verified at `database/backups/pre-day37-39-20261017T212017Z.db`; all original values across 38 tables survived upgrade to 0021 and integrity/foreign-key checks passed. The files are ordinary SQLite, **not encrypted by the application**. OS account/filesystem administrators control access. No automated backup schedule or expiry was found/added. No hosted PostgreSQL backup or restore was verified.

Restoration is an offline operator procedure: stop all writers, validate a private recovery copy, review the database/code migration pair, restore using the deployment's database tooling and recheck integrity/permissions. Never restore arbitrary user-uploaded files or expose backup directories through web routes. Backups may retain pre-deletion data until the operator's actual retention expires. Operators must record deletion-review requests outside a restored snapshot and reapply access closures/anonymization before reopening restored data. Commercial operation still needs reviewed backup encryption/access, retention/erasure procedures and a tested PostgreSQL restore exercise.

## Migration and deployment

New migrations: **0019** personal settings; **0020** notifications/preferences; **0021** private export/deletion-review metadata and nullable user/workspace closure timestamps. They are additive. Legacy care data is preserved. The legacy-only transfer guard recognizes head 0021 and refuses to discard nonempty new account/personal/history tables; it is not a general account migration tool. Downgrades refuse unreviewed data loss. Historical migration tests seed the actual historical schema with explicit SQL instead of asking today's ORM for future closure columns, and compare every original column value while allowing new nullable columns.

No new dependencies or environment variables. Existing Flask, SQLAlchemy, PostgreSQL/SQLite, Redis production limits, stable signing/mail-encryption keys, trusted HTTPS/proxy configuration and identity/invitation mail service remain required. Migrate before restarting web/worker processes. New commands must use exactly the deployment's database and stable application configuration.

```sh
venv/bin/python -m flask --app app backup-sqlite --source database/olumira.db --backup database/backups/before-premium-phase2.db
venv/bin/python -m flask --app app db upgrade
venv/bin/python -m flask --app app db current
venv/bin/python -m flask --app app process-reminders
venv/bin/python -m flask --app app privacy-maintenance
```

Use a new backup filename. PostgreSQL operators must take a native managed/database backup instead of invoking the SQLite command. Run reminders roughly every minute and maintenance daily via a supported scheduled job or external scheduler, with monitoring/retries. There is no Flask timer, automatic scheduler installation or claim that Render Free stays awake. Durable data survives process exit; notification generation requires the scheduled command to actually run. Command failure exits nonzero and redacts private records; earlier successfully committed member/profile batches remain and retries deduplicate them.

For code rollback, retain the compatible code/database pair and review recovery; do not reset/drop new records. No commit, push or deployment was performed. Live PostgreSQL, hosted schedules/monitoring, SMTP inbox delivery, load testing, physical erasure and formal accessibility certification remain deployment/release work, not claimed test results. Legal/privacy professionals must review intended users, jurisdictions, family/child data handling, retention and obligations before commercial collection. These technical controls are not a claim of HIPAA/COPPA/GDPR compliance.
