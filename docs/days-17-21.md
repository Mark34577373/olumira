## Architecture and portfolio explanation

Olumira now separates authentication from family authorization. An account may
have active memberships in several family workspaces. Each request resolves the
selected workspace against current database membership; a signed session stores
selection hints, never permission grants. Routines and observations carry an
explicit workspace relationship and optional care-profile relationship. Dashboard
metrics use exactly that authorized scope. This permits trusted caregivers to
collaborate without letting unrelated families read or change one another's data.

`services/workspaces.py` contains context resolution and the permission matrix.
`services/collaboration.py` owns invitation issuance, acceptance and member changes.
Workspace rows serialize writes before membership checks, providing one lock order
for both SQLite development and PostgreSQL. Role and membership state are read
from the database on each request. A read already authorized before a concurrent
revocation can finish; subsequent requests reload permissions. Information already
downloaded cannot be recalled.

### Models

| Model | Relationship and purpose |
| --- | --- |
| FamilyWorkspace | Private named family space; creator is provenance, not permission |
| WorkspaceMembership | Unique user/workspace pair, constrained role and active/revoked status |
| CareProfile | Workspace nickname, built-in illustration, optional bounded preferences |
| Routine / Observation | Nullable workspace for quarantined legacy records; optional profile |
| RoutineCompletion | Belongs to its scoped parent routine, preserving original IDs and history |
| WorkspaceInvitation | Workspace, normalized invited email, caregiver/viewer role, token digest, expiry/use/revocation |
| AuditEvent | Actor, workspace, event type, optional target ID, UTC time; no private content |
| EmailOutbox | Existing encrypted payload, now optionally associated with an invitation |

Names/preferences are escaped on output; sensitive fields are optional. No uploaded
photos, diagnoses, public profiles or third-party analytics were introduced.
Workspace-level routines are the explicit “Workspace routines” selection; selecting
a profile shows only its routines and observations, not an aggregate of all profiles.
Creating a profile does not silently reassign existing shared content.

### Permission matrix

| Capability | Owner | Caregiver | Viewer |
| --- | --- | --- | --- |
| Read workspace, profiles, routines, observations, member names/roles | Yes | Yes | Yes |
| Select workspace/profile; use transient built-in communication choices | Yes | Yes | Yes |
| Create/edit profiles, routines and observations; complete routines | Yes | Yes | No |
| Save browser-local communication customization | Yes | Yes | No |
| Rename workspace, invite/resend/revoke, change caregiver/viewer roles, remove non-owners | Yes | No | No |
| Read workspace audit trail and invitation email addresses | Yes | No | No |
| Grant owner, remove/demote owner, delete workspace | Unavailable | Unavailable | Unavailable |

The centralized matrix denies unknown capabilities. Existing routine/observation
POSTs are checked in the factory hook with their specific permission. Workspace
routes use `require()` and mutation services repeat authorization under the
workspace lock. Foreign resources and nonexistent resources return the same missing
response. Viewer controls are hidden or disabled, and direct requests are rejected.
No ownership-transfer feature exists: owners cannot be demoted or removed, so the
final owner cannot be lost through these interfaces.

Communication customization remains browser-local, explicitly described in the UI.
Its new storage namespace includes user, workspace and profile. Earlier shared or
user-only keys are not imported. It is not a shared caregiver database. Transient
message selection writes no server state and is permitted for viewers. Developer
tools can alter local browser storage, but cannot grant server capabilities.

## Invitation lifecycle

Only active owners can invite caregivers or viewers. Addresses use the existing
normalizer; owner invitations are never accepted. Issuance locks the workspace,
rotates earlier pending invitations for the same email and cancels their unsent
outbox jobs. The verifier stores SHA-256 of a 256-bit random token. The raw token
exists only in the encrypted delivery payload and the recipient's email/form.
The URL uses a fragment, which the existing local script reads and removes from
history. Management screens never expose tokens. No GET consumes an invitation.

Acceptance requires a verified signed-in account whose current email matches the
invite. The workspace and account are locked; expiry, revocation, prior acceptance,
inviter ownership and existing membership are rechecked. Conditional token claiming
and a unique membership constraint prevent duplicate concurrent acceptance. A
revoked previous membership may be restored by a fresh invitation, with the newly
invited role. Success selects the workspace and clears the previous profile.
Resend rotates rather than reuses tokens; revocation and acceptance cancel unsent
messages. The mail worker rejects expired/revoked/accepted invitation jobs too.

The form POST remains CSRF protected even when a token is present. Invalid,
expired, wrong-email and used links produce one generic unavailable response.
Anonymous/unverified visitors receive account guidance without revealing workspace
information from a supplied token.

## Safe migrations and legacy records

Head is **0006**. Apply migrations before starting the new application version.

- 0004 adds workspace/membership tables and nullable workspace links. `INSERT SELECT`
  backfills only records matched to an existing account's explicit owner key. User
  IDs, hashes, verification flags, account/session tokens, care IDs and completions
  are preserved. No unclaimed owner is inferred from cookies or record timing.
- 0005 adds profiles and nullable profile links. All old content remains at workspace
  level. SQLite uses additive `ALTER TABLE ... REFERENCES` statements, avoiding a
  parent-table rebuild that could cascade-delete routine completions. Database
  enforcement rejects cross-workspace profile associations.
- 0006 adds invitations and audit events, and links encrypted outbox jobs to invites.
  Audit records reject update/delete operations at the database level.

The old ownership columns remain provenance/offline-maintenance fields; HTTP queries
use explicit workspace and selected-profile constraints. Offline legacy-only import
refuses any source or destination containing account/workspace/collaboration data.
It is not an account migration tool. Unknown legacy records stay private until a
separately reviewed ownership-establishment procedure authorizes a transfer.

Downgrades deliberately refuse destructive schema removal. Recovery means stopping
writes and restoring a verified database backup with the matching application
version. Do not restore an old backup over later valid writes without a recovery
plan. PostgreSQL migrations are transactional; SQLite DDL can be nontransactional,
so quiesce the app and take a verified backup first. A failed partial SQLite DDL
upgrade should be recovered from backup, not blindly rerun.

## Development and repeatable fictional demonstration

Install `requirements-dev.txt`, run `flask --app app db upgrade`, then run
`PUBLIC_APP_URL=http://127.0.0.1:5000 venv/bin/python -m flask --app app run --port 5000`.
The default canonical local origin now matches port 5000; set it explicitly if using
another port. Configuration uses environment variables, not automatic `.env` loading.

For an ordinary private local email preview:

```sh
venv/bin/flask --app app mail-queue
venv/bin/flask --app app mail-preview --message-id MESSAGE_ID --output database/mail-preview/unique-name.eml
```

Open that private file locally and follow the link, or paste its code on the linked
page. The CLI refuses overwrites and production previews; files are mode 0600 and
ignored by Git. Do not paste codes into logs or commit previews. No SMTP connection
is made in development. Production delivery requires a configured provider and the
outbox worker; changing the backend alone does not deliver messages.

For a repeatable, fully fictional demo with no shared credentials or persistent
care data, run:

```sh
venv/bin/python tests/browser/check_workspaces.py
```

It creates a temporary database and three independent browser contexts, registers
and actually verifies fictional accounts using their encrypted test inboxes,
creates “Fictional Cedar Family” and “Fictional Fern”, adds care content, accepts a
new-account caregiver invitation, demonstrates shared editing, proves unrelated
family denial, accepts a viewer invitation, and demonstrates live role demotion and
member removal. It captures screenshots and a sanitized JSON report under
`artifacts/days17-21`. The temporary database is removed afterward; no public demo
administrator or shared password is created.

## Deployment checklist and remaining limits

Before any deployment:

1. Back up the actual database, verify integrity and rehearse recovery. Rehearse
   0003→0006 against a staging copy with record comparisons, not real demo data.
2. Configure `APP_ENV=production`, strong stable `SECRET_KEY`, PostgreSQL
   `DATABASE_URL`, shared Redis `RATELIMIT_STORAGE_URI`, HTTPS `PUBLIC_APP_URL`,
   independent `MAIL_ENCRYPTION_KEY`, verified sender and authenticated TLS SMTP.
3. Set `INVITATION_SECONDS` (default 86400; allowed 60–86400). Review proxy hops and
   trusted hosts against the hosting topology. Do not expose development secrets.
4. Quiesce writes, apply reviewed migrations, then start `gunicorn app:app`.
5. Schedule `flask --app app mail-send-pending --limit 20` every minute using the same
   database and encryption key. Monitor retries and failures without message bodies.
   SQLite development supports one mail worker; PostgreSQL uses locked job claiming.
6. Verify real registration, actual inbox delivery, recovery and invitation links,
   shared membership, role enforcement, cross-family denial and session revocation
   against staging PostgreSQL/Redis/SMTP. Confirm HTTPS cookie/header behavior.
7. Resolve or explicitly assess the dependency findings in the security review.
   Do not treat mocked SMTP or SQLite concurrency as proof of hosted operation.
8. Keep public real-caregiver onboarding disabled until privacy, access/retention,
   account deletion/export, incident handling and security requirements are reviewed.

Retention is deliberately non-destructive: no automatic deletion of workspace,
profile or audit history. Revocation retains records and audit provenance. Audit
history is protected from application changes, but a database administrator remains
trusted and could alter schema/triggers. A consent-based export/deletion process,
mail/token cleanup schedule, backup retention and legal requirements need operational
review before collecting real care data. These are not silently enabled features.

No ownership transfer, workspace/profile deletion, uploads, shared persisted custom
communication cards, real SMTP credentials, live PostgreSQL/Redis environment,
formal accessibility audit or independent penetration test is included. The app
uses bounded free-text preferences, not encrypted-at-rest clinical records; secure
hosting, database/backup encryption and administrator access controls are operator
responsibilities. Mail uses an at-least-once outbox; a worker crash after SMTP accept
can cause duplicate delivery, while invitation use remains single-use.
